# MemoryTopologyPanel

| spec-id-prefix |
|----------------|
| PR-MEMTOP-*    |

Official product memory-path topology chrome with **data-driven link values** (change-log #5, UI-38).

## Inputs

**model** — `MemoryTopologyModel` (`nodes` + `edges`; each edge carries an optional data-driven `label`; the `l2` node may carry `peakPct`; optional `plates` for the in-box unit badges, UI-49). Optional **locale**. Optional **openDetailsOnContextmenu** (default true): stacked diagram keeps UI-35; the root fullscreen overlay passes `false`. Optional **showFullscreen** (default false): the bar renders its **全屏** control, so the stacked aside asks the host to cover the report; the root overlay is already full and leaves it off. Parent `StatsAside` owns block switching and rebuilds **model** via `buildMemoryTopology`, passing the Memory* CSVs **plus** `PipeUtilization.csv` (the badges' source).

## Outputs

**open-details** — UI-35: right-click on the stacked diagram opens the parent memory CSV overlay (same as **详情**). Not emitted when `openDetailsOnContextmenu` is false (fullscreen overlay).

**open-fullscreen** — the bar's **全屏** control (only rendered when **showFullscreen**) asks the host to cover the report with the diagram. The panel does not open the overlay itself; the host owns the dialog (PR-MEMTOP-014).

## Behavior

1. Render the official chrome asset `memory-topology.svg` (Figma export of `v930/report-stats-scrolled` 内存负载分析, 448×540 units) at full size. Everything static lives in the asset and is **not** drawn by this component: GM/HBM → L2 → AIC (L1, L0A/B/C, Cube, FixP, Scalar) and AIV0/AIV1 (UB, SIMT/SIMD, Vec, Scalar, DCache, MTE1/2/3, FixPipe, BT/FB/SS), the `XN_IMM` / `Data Cache` nodes, boxes, arrows, dashes and the value plates ([VIEW_DATA_MAPPING §11.2.6](../../../../docs/ui/VIEW_DATA_MAPPING.md)). Because the chrome owns the arrows, the panel renders no SVG `<marker>`s.
2. Overlay the values from `model.edges` as SVG `<text>` at the **value slots** below — the centres of the placeholder values that were stripped from the export.
3. One `<text>` per slot is always drawn, including when the edge has no `label` (empty content). The adapter hides `NA` and formats `0`, so an omitted value leaves a visibly blank plate rather than a missing node.
4. Slot geometry is fixed; only the text is data-driven. A pair's upper slot rides the link whose arrowhead points into the right-hand box (GM→L2, L2→UB, UB→SIMD, Cube→L0C).
5. Values follow the **model** the parent passes; when the parent rebuilds for a new `block_id`, values update.
6. Hide the diagram (empty root) when `model` is absent, or when nothing drawable remains: no slotted edge label and no L2 plate (`peakPct` / `l2-hit`). Slotless labelled edges alone do not mount the chrome.
7. **L2 Peak(%) (DATA-20):** when the `l2` node has `peakPct`, show `{n}%` in the export's in-box plate under **L2 Cache** (no “Peak” word, no warm tint). Otherwise fall back to the `l2-hit` edge label in the same plate; never both. **No other unit carries a Peak(%):** the export gives GM / L1 / L0A / L0B / L0C / Cube / FixP / UB / Vec / Scalar no plate to print one in, and the adapter produces no value for one — L2's is the only peak plate (`TOPOLOGY_PEAK_PLATE_EDGE_ID = 'l2-hit'`). The **other** in-box badges the sketch draws are plain unit **utilizations**, not peaks — item 7b.
7b. **In-box unit badges (UI-49, "other" plates):** paint `model.plates` as `{n}%` in the unit's own box, under its own word, at `PLATE_SLOTS`: AIV0 **and** AIV1 `Scalar` (one field, `aiv_scalar_ratio`, drawn in both rows), AIV0/AIV1 `Vec` (`aiv_vec_ratio`), `Cube` (`aic_cube_ratio`). The ratio is the unit's utilization of its **own** busy time (DATA-28) — the same ratio the 计算负载分析 pipe rows show, printed at the sketch's **two decimals** (`57.90%`, where the pipe row rounds to `58%`) — so `{ratio × 100}` is the label. Iteration is keyed by the adapter's `TOPOLOGY_PLATE_NODE_IDS`, so a newly plated unit without coordinates fails typecheck (same rule as the link slots). A unit the model gives no value is **not drawn at all** — the sketch's **four** field-less badge positions (`AIC Scalar`, AIV0/AIV1 `SIMT`, `FixP`) stay blank by absence, not by an empty `<text>`. The producer's six `NA` rows include the AIV0/AIV1 `SIMD VF` pair, but those rows describe the `Vec` position, which the `Vec` rows (`6'`/`7'`) fill — so that position is painted, not blank.
8. **Right-click (UI-35):** `contextmenu` on the diagram prevent-defaults. When `openDetailsOnContextmenu` is true (stacked aside), emit `open-details` so the parent opens the memory CSV overlay (Memory / L2Cache / MemoryUB / MemoryL0). When false (root fullscreen overlay), do not emit; overlay stays open. The gesture is the **diagram's**: the bar is inside this panel, so a right-click on a control — or on the strip between them — prevent-defaults and does not emit (PR-MEMTOP-008c).
9. Fullscreen chrome (Back, dialog shell) lives on `ProfilingReport`; this panel contributes the bar's **全屏** control and emits `open-fullscreen` for it (PR-MEMTOP-014). The panel stays presentational — it never mounts the overlay.
10. **Value fit (PR-MEMTOP-010):** a value wider than its own slot's corridor is drawn at a proportionally smaller `font-size` so it stays inside the link, instead of overlapping a pillar or a neighbouring unit. Values that fit keep the base size; nothing else about the slot moves. In-box badges use their own, tighter wall table (`PLATE_MAX_W`) — they must stay inside their **box**, not a corridor.
11. **Accessible description (PR-MEMTOP-011):** the root `role="img"` makes the diagram one image, so its `<text>` values do not reach the a11y tree by themselves. The panel therefore also renders a visually hidden list of the slots it draws — `{from} → {to}: {value}` once per edge (paired AIV0/AIV1 slots add `(AIV0, AIV1)`) plus the L2 plate and the in-box badges (one entry per unit, so the pairs are named once) — and points the `svg` at it with `aria-describedby`. Slots left blank and edges with no slot are omitted. Each instance uses its own id (`useId`), because the stacked aside and the fullscreen overlay render two panels at once.
12. **Slot testids (PR-MEMTOP-002b):** `data-testid` is `edge-{edge-id}-{slotIndex}` for link values and `plate-{node}-{slotIndex}` for in-box badges, so the AIV0/AIV1 pairs resolve to distinct elements.
13. **Chrome load failure (PR-MEMTOP-012):** if the `<image>` errors, warn once, suppress value overlays (link values and in-box badges alike), and clear `aria-describedby` so hosts missing `/memory-topology.svg` do not see orphaned numbers or a dangling description id. The bar goes with it: a zoom control over a diagram that failed to load is dead chrome.
14. **Zoom / fullscreen bar (PR-MEMTOP-014):** under the diagram, aligned to the panel's end, on its own `#313131` strip (the v930-sim export's 5% lift over the `#262626` card). Controls in the export's order: **缩小** (−), the current readout (`100%`), **放大** (+), **适应窗口** (the accent control), and — only when **showFullscreen** — **全屏**. Each control is a `<button>` with `aria-label`/`title` from i18n (`zoomOut` / `zoomIn` / `zoomFit` / `fullscreen`); the readout is `aria-live="polite"` so keyboard zooming is announced. The strip belongs to the stacked bar: the export's fullscreen frame has none, so the root overlay drops it and its controls sit straight on the card (a host override, not a second bar — the panel's markup is the same in both).
15. **Zoom (PR-MEMTOP-015):** the readout walks a discrete ladder — `50, 75, 100, 125, 150, 200, 300, 400` (%) — one stop per **+**/**−**; at either end the control is disabled rather than a no-op. **100% is fitted to the box**, not 1:1 chrome units: the panel has no fixed pixel budget (the stacked aside and the root overlay differ), so 100% is the one scale that is right in both, and the diagram keeps filling the panel exactly as before this control existed. **适应窗口** returns to 100% *and* to the scroll origin, and so does stepping back down to a fitted stop — a diagram panned while zoomed in comes back to its top-left corner rather than to an offset the box can no longer show (PR-MEMTOP-013).
16. **Zoom geometry (PR-MEMTOP-013):** the diagram sits in a fit box of the chrome's own 448:540 ratio, and inside it a **stage** that is the *diagram's* own box — `--pr-topo-zoom` times the window's height, with the width following the chrome ratio from that height, so the drawing fills the stage exactly. Zoom scales that stage; the box around it is unchanged, and a zoomed diagram is panned with the scroll the box already has — its own bars (PR-MEMTOP-013) and a drag on the drawing (PR-MEMTOP-017) — with no transform on the panel. Sizing the stage from the *window* in both axes is only right where the window already has the chrome ratio (the stacked aside); in the wide overlay it left the scroll travelling through empty stage (measured at 125% there: a 1955×963 stage around a 799×963 drawing, i.e. 391px of a 391px horizontal range was blank), so the pan now covers the diagram's own overflow in both hosts.
    At or below the fit the diagram is **centred** in the box, and the fitted box is **not a scroll container at all** and shows no scrollbar. It would otherwise be one over nothing: the box's height comes from `aspect-ratio` while the diagram's comes from its own intrinsic ratio, and the two agree only to a rounding step (511 vs 511.0625 in Chrome), which is enough to paint a stray permanent scrollbar wherever a platform does not snap that overhang away. Centring is a fitted-state rule only — a centred item that overflows would leave its own start edge unreachable, which is why the panning state aligns the stage to the box.
    jsdom has no layout, so this geometry is asserted in the browser: `tests/e2e/topology-zoom-geometry.spec.ts` measures the drawing's 448:540 ratio, the fitted state filling its box, and the scroll range against the drawing's own overflow in the aside **and** in the overlay.
17. **Drag to pan (PR-MEMTOP-017):** past the fit the drawing itself is a pan surface, not only the bars: a **primary-button drag** on the diagram scrolls the box 1:1 with the pointer (the content follows the cursor), writing the same `scrollLeft` / `scrollTop` the bars write, so a drag and a thumb drag cannot disagree and no second offset is stored. The cursor is `grab` on a draggable diagram and `grabbing` for the length of the gesture; the press is captured, so the drag survives leaving the box, and it neither selects the chrome's `<text>` values nor starts the platform's own image drag. At or below the fit there is nothing to pan, so the drag is a no-op and the cursor stays plain. Two presses are **not** pans: a non-primary button, and a press that begins on a **classic** scrollbar — the thumb reports its press on the box too, and panning from `clientX` alongside it would fight the platform's drag. That test is measured against the box (`clientWidth` / `clientHeight` from the box's own rectangle), **not** against `offsetX`: Chromium reports `offsetX` against the **content**, so it walks with the pan and would read an ordinary press near the right edge as a thumb once the diagram was scrolled (measured in the browser: a press 21px inside a 424px box at `scrollLeft: 70` reports `offsetX: 473`). Overlay bars are drawn over the drawing and cannot be told apart from it — a press on one pans, and the drag's `grab` affordance is the same anywhere in the box that is not a classic gutter. **Touch is left to the platform, and a touch press does not arm the drag at all** (`pointerType === 'touch'` returns before the capture): Chromium's own touch scroll is the same pan, and capturing the finger would delay or suppress the `pointercancel` that hands the gesture over. A `touch-action: none` would give the diagram the drag's 1:1 feel but would also take away native touch scrolling and pinch for every user, so it is deliberately not set. `pointercancel` still ends a live drag, for a takeover that is not touch. The drag does not zoom, does not move the report behind the overlay, and does not replace the wheel.
18. **Zoom keeps the middle (PR-MEMTOP-018):** a step on the ladder changes the scale and then places the scroll offset so that the part of the drawing under the middle of the box is still under it — the diagram grows around what is being looked at instead of away from its top-left corner, and the fitted start (whose middle *is* the drawing's middle) becomes a zoom about the drawing itself. The anchor is the middle as a fraction of what the box can **scroll** — `(scrollLeft + clientWidth / 2) / scrollWidth`, and the same on `y` — so there is no second copy of the stage's size or of its offset to keep in step with the CSS: the bars' own geometry already says where the content is, and reading it against the *scrollable* extent is what also makes it hold in the fitted state, where the stage is centred by `margin-inline: auto` and `scrollWidth` is still the box's own width (the middle is then exactly half of it). It is measured **before** the step and applied **after** it, because the placement needs the new scale's `scrollWidth`: stepping up from the fit therefore lands on the middle of that axis' own overflow, and a panned diagram zooms about what is on screen rather than about the drawing's centre. A step **down to a fitted stop** is unchanged — it still returns to the origin (PR-MEMTOP-015), since a box that no longer scrolls has no fraction to keep — and a box with no layout (jsdom, `clientWidth === 0`) has no middle to keep and is left exactly as it was.
19. **A step is tweened, not snapped (PR-MEMTOP-019):** **放大** / **缩小** / **适应窗口** commit the new stop at once — the readout, the ladder ends and `pannable` move on the click, so a second click steps from the stop that was *asked for* rather than from a frame still in flight, and four quick **放大** are still four stops — while the **drawing** travels to it over the project's own `animateProgress` tween (400ms ease-in-out cubic, the same curve and timing as the timeline's zoom-to-fit). The scale actually painted on a frame is what sizes the stage and drives `pannable` (the committed stop is only what the readout and the ladder read), and the middle of the box is re-placed against that scale on every frame, so the anchoring of PR-MEMTOP-018 holds for the whole flight and not only at its ends. A step asked for mid-flight cancels the one running and takes a **fresh anchor off the scale now painted**, so a re-click grows the drawing from where it is instead of snapping back to where the previous step had aimed. Under `prefers-reduced-motion: reduce` the tween is skipped by `animateProgress` itself and the step lands on the click, spending no frame at all. `data-topo-zoom-animating` marks the flight (`true` for its length) so a test can settle on it — the unit test drives the frames by hand, and the flight through a real box is measured in `tests/e2e/topology-zoom-geometry.spec.ts`.

### Value fit (PR-MEMTOP-010)

The export's slots were sized for its own 27.6-unit placeholders. Real values are longer (`{n}.{nn} GB/s`, KB volumes) and the system sans is wider per cap height than the export's face (~1.2×), so a label can outgrow its link. Each slot has a **corridor** — the free run between the chrome around it, measured off the export at the value's own height band. A value is drawn centred on its slot, not on the corridor, so the binding constraint is the **nearer** wall:

| Slot | Corridor (walls, chrome units) | Bound |
|------|-------------------------------|-------|
| `gm-l2-read` / `gm-l2-write` | x≈55.75 … x≈94 | 35.4 |
| `l2-ub`, `ub-l2`, `l2-l1-read` | x≈133.75 … x≈188 | 49.9 |
| `ub-vec` / `vec-ub` | x≈315 … x≈361 | 42.1 |
| `l1-l0a` / `l1-l0b` | x≈217 … x≈262 | 41.1 / 40.3 |
| `l0a-cube` / `l0b-cube` | x≈282 … x≈322 | 36.7 / 34.7 |
| `cube-l0c` / `l0c-cube` | x≈353 … x≈394 | 37.5 |
| L2 plate (`peakPct` / `l2-hit`) | x≈94 … x≈133.75 (the pillar) | 36 |

**Every** slot carries its own bound (`SLOT_MAX_W`): the row stack's inner corridors are far tighter than the pillars' (L0B↔Cube is 34.7 against L2↔row's 49.9), so no single bound serves them all. A slot the table forgets falls back to the **tightest** bound (34.7) — a generous fallback would silently overflow a narrow corridor. A value whose natural width exceeds its bound is drawn at `bound / natural × 6.3px` — the same strokes, scaled down — so e.g. `504.00 GB/s` (43.2 units) lands at 5.17px inside the GM↔L2 link and at 5.06px inside L0B↔Cube. Widths come from the rendered label's own metrics (`getComputedTextLength`), so they follow the platform font; where metrics are unavailable — a non-browser DOM, or a mount inside a hidden container, where text has no layout and measures 0 — the panel keeps the base size.

**In-box badges** measure against their **box**, not a corridor (`PLATE_MAX_W`, passed as the bound table to the same `fitFontSize`): the `Scalar` and `Cube` boxes are ~30 units wide, the `Vec` box only ~22 — the sketch's own `2.18%` badge already fills 17 of them — so the bound is the box's inner width minus a small margin:

| Plate | Box (walls, chrome units) | Bound |
|-------|---------------------------|-------|
| `aiv_scalar` | x≈266.5 … x≈297.5 | 26.5 |
| `vec` | x≈361.5 … x≈382.5 | 18.5 |
| `cube` | x≈322.5 … x≈353.5 | 28.5 |

A `100.00%` badge (31.1 units) therefore shrinks in all three boxes, the `Vec` one the most; a `2.18%` badge shrinks only in `Vec`. The corridor table is untouched — the two kinds of slot never share bounds.

**No slot —** `l0c-l1` / `l0c-l2` (L0C→L1 / L0C→GM data volumes, KB) have no plate in the export, which carries no KB values; they stay in the Memory.csv 详情 tabs. The same is true of the AIV0/AIV1 SIMT in/out pair, the four in-row SIMT links per AIV row, the UB→VEC run, the two rotated AIV↔AIC trunk labels, AIC `L1→MTE1#3→BT`, `FixP→rail`, the FixP-routed lower L2↔AIC corridor (`l2-l1-write`, pending [UI-48](../../../../docs/context/questions/UI.md)), and the **four** in-box badge positions with no producer field (UI-49, below). Several of these slotless positions **do** carry a value in the sketch, and three corridors carry more values than the export has plates for — that sketch-ward audit is [DATA-42](../../../../docs/context/decisions/DATA.md) (**resolved** 2026-09-15): the producer gives every unplated link position `字段: NA`, so there is no field to read and the **13 plated corridors above are the complete set**.

**MTE blocks (UI-38) —** the chrome draws `MTE1`/`MTE2`/`MTE3` boxes (AIV0/AIV1 columns, the AIC column and the L2↔cluster trunk), but the export gives every one of them **no value plate**, so the panel draws no slot for MTE and the diagram stays exactly as designed. The blocks are modelled as nodes (`mte1`/`mte2`/`mte3`) and their utilizations are read from `PipeUtilization.csv` in the memory 详情 **CSV field list** (CSV-only reports — [StatsAside](../StatsAside.spec.md) PR-STATS-035); summary-category reports keep MTE under 计算 详情.

**In-box plate inventory (2026-09-15, resolved) —** this note first claimed the export carries "10 in-box `%` plates (L2, UB/Scalar, CUBE/FixP, SIMT/SIMD/VEC)" and then retracted the claim as unreproducible. Product resolved UI-49 by painting the three units that **have** a field at the sketch's own positions (item 7b / `PLATE_SLOTS`) and leaving the **four** field-less badge positions blank (the producer's `SIMD VF` rows name the same in-box position the painted `Vec` rows fill): the export still has no plate rect for any of them, so the panel draws the badges at measured sketch coordinates instead of into export chrome. The AIC row's blank values on the product fixture stay [DATA-41](../../../../docs/context/questions/DATA.md).

## Acceptance Criteria

1. **PR-MEMTOP-001** — Renders the chrome asset `memory-topology.svg` at 448×540 with the L2 node anchor.
2. **PR-MEMTOP-002** — Renders data-driven edge labels (GB/s) from `model.edges`; Vec↔UB on AIV0 and AIV1; AIC L1/L0/Cube labels when present.
2b. **PR-MEMTOP-002b** — Every drawn value carries a unique `data-testid` (`edge-{edge-id}-{slot}`), so a `getByTestId`-style query resolves to one element even for the AIV0/AIV1 pairs.
3. **PR-MEMTOP-003** — Omits the label for an edge with no `label` (slot drawn, blank).
4. **PR-MEMTOP-004** — Hides the diagram when `model` is null/empty, or when the only labelled edges have no chrome slot (and there is no L2 plate).
5. **PR-MEMTOP-005** — Edge labels update when `model.edges` labels change.
6. **PR-MEMTOP-006** — GM↔L2 labels sit between the GM and L2 pillars; L2↔cluster labels sit between the L2 pillar and the row stack. The export draws these horizontally in the corridor (the earlier redraw rotated them).
7. **PR-MEMTOP-007** — When `l2.peakPct` is set, shows `{n}%` in the L2 plate (no “Peak” word) and hides the `l2-hit` edge label.
7b. **PR-MEMTOP-007b** — Omits Peak chrome when `peakPct` is absent.
7c. **PR-MEMTOP-007c** — With `peakPct` absent, the same single plate shows the `l2-hit` edge label; the two sources never both render.
8. **PR-MEMTOP-008** — Right-click emits `open-details`.
8b. **PR-MEMTOP-008b** — Right-click does not emit when `openDetailsOnContextmenu` is false.
